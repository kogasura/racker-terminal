# フロントエンドのアーキテクチャ方針

`src/features/updater/` が、この方針を全部適用した参照実装です。新しく機能を足すときは
そちらを読んでから、同じ形で書いてください。

`src/features/tabs/` は、**データを store に残したまま**この形へ寄せた例です。
Mediator が裁定するのはキーコマンドを通すかどうかまでで、通ったコマンドは効果として
store のアクションに落ちます（`effects.ts` が唯一の接点）。既存機能を段階的に移すときは
こちらの形が出発点になります。

## 4 つの決まりごと

### 1. すべてのコンポーネントは Root の配下に置く

機能ごとに Root を 1 つ持ち、その機能に属する View は必ずその内側に置きます。
Root は `src/Roots.tsx` でまとめて敷き、**`App` を含むすべてのコンポーネント**が
その配下に入ります（`App` 自身も副作用の中からイベントを流すため）。
Root が持つのは次の 3 つだけです。

- Mediator（ステートマシン）の生成と保持
- イベントチェーンに自分のリンクを挿す（`mediatorLink('<接頭辞>/', send)`）
- 状態 → View モデルの射影を子へ配る

Root は**終端（`tail`）を指定しません**。終端を乗っ取ると他機能宛てのイベントまで
飲み込んでしまい、Root を入れ子にできなくなります。自分宛て（イベント名の接頭辞が
一致するもの）だけを Mediator に渡し、それ以外は上へ流します。

View が DOM 上は離れた場所に出ることがあります（更新バッジはタイトルバーの中、
設定セクションは設定ダイアログの中）。その場合でも Root は**コンテキストの親**として
上位に居ればよく、DOM の親子である必要はありません。

### 2. 各コンポーネントは Passive View にする

View は、描画に必要な値（View モデル）を受け取って並べ、起きたことを上へ流すだけです。

- store を直接読まない（`useAppStore` を呼ばない）
- 判断をしない。「ボタンを押せるか」「何と表示するか」「そもそも出すか」は
  すべて `viewModel.ts` の射影関数が決めて、真偽値と文字列にして渡します
- 自前の状態を持たない。持ちたくなったらそれは Mediator の状態です

判断を View から追い出すと、見た目の仕様を**レンダリングせずに**テストできます
(`viewModel.test.ts` がそれです)。

### 3. 動作は Chain of Responsibility でバブリングさせる

View は `useEmit()` で得た関数にイベントを投げるだけです。どこで処理されるか、
そもそも処理されるのかを View は知りません。

イベントは最も近い `EventScope` のリンク列を通り、処理されなければ親のスコープへ、
最終的に Root の Mediator まで昇ります。各リンクは `next(event)` を呼べば上へ流し、
呼ばなければそこで消費します。イベントを書き換えて渡すこともできます。

イベント名は「何が起きたか」で付けます。`apply-requested` であって `install` ではありません。
命令形にした時点で、View が「次に何をすべきか」を決めてしまっています。

### 4. Mediator はステートマシンとして裁定する

状態は判別可能なユニオンで表し、ありえない組み合わせを型で消します。
`updater` の場合、以前は `updatePhase` / `updateDialogOpen` / `updateError` /
`updateInfo` という独立したフラグの組み合わせだったため、「idle なのにダイアログが
開いている」「error なのに理由が null」といった状態を作れてしまっていました。

遷移関数は**純粋**に保ちます。「今の状態 + 来たイベント」から「次の状態 + 実行したい
副作用」を返すだけで、非同期も I/O もしません。実際に副作用を回すのは `effects.ts` で、
結果はイベントとしてマシンへ戻ります。

遷移関数が `null` を返したら「その状態ではそのイベントは意味を持たない」という意思表示で、
状態も通知も動きません。**無効な操作を弾く場所はここ 1 箇所だけ**です。View 側でも
`disabled` を出しますが、それは見た目の話であって、防御ではありません。

## ファイルの分け方

```
features/<名前>/
  events.ts       イベント定義 (View から上がる操作 / 副作用から返る結果)
  machine.ts      状態・遷移・副作用の宣言。純粋。
  effects.ts      副作用の実行。ここだけが I/O を持つ。
  viewModel.ts    状態 → 描画パラメータの射影。純粋。
  <名前>Root.tsx  Root
  views/          Passive View
```

テストの置きどころもこの分割に従います。遷移の網羅は `machine.test.ts`（非同期なし）、
見た目の仕様は `viewModel.test.ts`（レンダリングなし）、副作用と絡む振る舞いだけを
`integration.test.ts` で見ます。

## 例外: 命令的リソースを抱えるコンポーネント

Passive View の条件を満たせないものが 1 種類だけあります。**外部ライブラリの命令的な
インスタンスを保持し、React の外から発火するコールバックを受けるコンポーネント**です。
いまのところ `TerminalPane` が抱える xterm.js の `Terminal` がこれにあたります。
画面の内容は「描画パラメータ」では表せず、`write()` で流し込むしかありません。

この 1 点は例外として認めます。ただし**例外の範囲は「その命令的リソースの世話」だけ**で、
コンポーネント全体が自由になるわけではありません。

### 例外として認めること

- 命令的インスタンスの生成・破棄・書き込み・フォーカスを直接呼ぶこと
- そのインスタンスが React の外から発火するコールバック（PTY の出力、OSC シーケンス）の
  配線に、store のアクションを直接渡すこと

### 例外でも守ること

- **判断はしない。** 何を起動するか、いつ失敗扱いにするか、といった決定は Mediator の仕事です
- **リソースの寿命は View モデルが決める。** いつ作っていつ壊すかを自分で判断しない
- **ユーザー操作はイベントとして上へ流す。** そのキーがたまたまこのコンポーネント上で
  押されただけなら、それは例外の対象外です

### 境界の具体例（`TerminalPane` の現状）

移行前の `TerminalPane` には store 参照が 17 箇所ありましたが、例外に当たるのはこのうち
**7 箇所だけ**です。残りは通常どおりイベントに置き換えます。

| 分類 | 箇所 | 扱い |
|---|---|---|
| ランタイムの生成とコールバック配線（`settings` / `setTabStatus` / `updateTabOscTitle` / `isEditing` / `onCwdChange` / `onAgentState` / `onTabStatusOsc`） | 7 | **例外。** そのまま直接触ってよい |
| Ctrl 系キーバインドからのアプリ操作（タブを閉じる・移動・復元・新規・お気に入り起動、コンテキストメニュー中の抑止） | 7 | 例外ではない。**移行済み** → `features/tabs/` |
| 起動シーケンスの決定（Claude セッションの採番、起動プランの算出、spawn タイムアウトの失敗判定） | 3 | 例外ではない。Mediator（ステートマシン）へ移す。`spawning → live / crashed` は素直に状態遷移になる。**未着手** |

つまり「`TerminalPane` は例外」ではなく、「`TerminalPane` の中の**ターミナル面の世話**が
例外」です。キー入力の受け口とタブの起動フローは、他の機能と同じ形に寄せられます。

## 移行の状況

| 機能 | 状態 |
|---|---|
| `features/updater/` | 完了。状態もデータも Mediator が持つ |
| `features/claudeStatus/` | 完了。`StatusBar` は store 参照 0 の Passive View。プラン利用量のポーリングも Root が持つ |
| `features/tabs/` | キーコマンドの裁定、コンテキストメニューによる抑止、`TabBar` / `Sidebar` の View モデル。タブのデータ（`groups` / `tabs` / `favorites`）はまだ store |
| それ以外 | 未着手。`useAppStore` を直接参照する従来の形 |

Passive View になったもの: `TitleBar` / `StatusBar` / `TabBar` / `Sidebar` /
`TabItem` / `GroupSection` / `FavoritesSection` / updater の View 群。
**画面の枠 (タイトルバー・サイドバー・タブバー・ステータスバー) は、
これで全部 View モデル経由になった。**

D&D も移した。ドラッグは「掴んでいる / いない」という状態そのものなので、
store の `dragId` / `dragKind` という 2 つのフラグをやめて Mediator の状態にした
（「id はあるが kind が無い」の組み合わせが作れなくなった）。落とし先の解決は
effects が持つ。

**View からも `App.tsx` からも store 参照が消えた。** `App.tsx` は 45 行の
構成だけになり、副作用はすべて機能ごとの Root が持つ。残るのは
`TerminalPane` 12（うち 7 は例外）だけ。`Roots.tsx` の 3 は hydration 待ちで、
Root 自身の仕事。

### 状態を持たない Root

副作用だけを持つ Root もある（`settings` / `terminalUpkeep` / `prStatus` /
`notifications`）。定期的な手入れや外部データの取得はユーザー操作が起点では
ないので、裁定するものがなく、Mediator の状態もイベントも要らない。

それでも機能ごとの Root にまとめる価値はある。`App.tsx` に並んでいたときは
「なぜここにあるのか」が読み取れず、`useEffect` の列から目的を再構成する
必要があった。対象ごとに分けると、ファイル名が目的になる。

### I/O は View に持たせない

「フォルダを選んで開く」は、以前 View がフォルダ選択ダイアログを開いて結果から
タブを作っていた。いまは View が「どのシェルで開きたいか」を流すだけで、
ダイアログの表示も effects の担当。View に I/O が残ると、そこだけテストで
踏めなくなる。

### 一覧の中の View モデル

タブ 1 個ぶんの View モデルは `useTabItemView(tabId)`、グループ 1 行ぶんは
`useGroupView(groupId)` で引きます。一覧ぶんをまとめて Root から配ると、
1 件の変化で全件が描き直されるためです。移行前のコンポーネントが個別に
subscribe していたのと同じ性質を保っています。

一方、お気に入り一覧 (`useFavoritesView`) はサイドバーに 1 つしか無いので
引数を取りません。**引数で絞るのは、同じ View が並ぶときだけ**です。

View から見れば「Root から降ってくる View モデル」であることに変わりはなく、
store の形も、そこから何を導くかも知らないままでいられます。

### コマンドの出どころで扱いが変わる

キーボード由来の操作（`TabsIntent`）は、コンテキストメニューが開いている間は
Mediator が捨てます。メニュー表示中でもキーイベントはターミナルまで届くためです。

ポインタ由来の操作（`TabsPointerIntent`）は止めません。メニューが開いているときに
ボタンを押せば、まずメニューが閉じてからクリックが届くので、誤爆の経路がそもそも
ありません。**止める理由がないものを止めると、それは仕様変更になります。**

残っている大きな塊は、`TerminalPane` の起動シーケンス（Claude セッションの採番、
起動プランの算出、spawn タイムアウトの失敗判定）です。`spawning → live / crashed` は
そのまま状態遷移になるので、次に移すならここです。

既存コードを触るときは、この形に寄せられないか一度検討してください。
